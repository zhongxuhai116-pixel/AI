### 2.2 灰模原因来自实际输入素材

- GLB 长度 9,050,600 bytes，SHA-256：`91aca93dde75840a7cca5a47dbffeb23395b3d81a054c42d44437233ebb8eebf`。
- meshes=1，materials=1，images=0，textures=0。
- 唯一材质：baseColorFactor=[0.22,0.22,0.22,1]，metallicFactor=0，roughnessFactor=0.5。
- primitive attributes 只有 POSITION；没有 TEXCOORD_0，也没有 COLOR_0。
- 因此缺少黑色面罩、蓝紫镜头和分区材质不是“Blender 未执行”，而是当前输入本身没有这些外观信息。单纯重跑、增加采样或提高分辨率不能补出可信材质。

## 3. BUG 与修改要求

### BUG-01 / P1：总时长是不可操作的假下拉，生成请求固定 6 秒

- 状态：**浏览器复现 + 代码确认**。
- 复现：项目 → 总时长“6 秒” → 点击；没有选项，只有焦点变化。视频比例与帧率采用相同无事件按钮。
- 原因：`apps/web/src/App.jsx:153` 的 button 无 onClick；`generatePlan`（2223）和 `aiGenerate`（2281）写死 duration_seconds=6；Shots（202）写死 3 SHOTS / 144 帧。
- 修改：区分基础预演与 V6 生产计划。前者提供后端支持的时长；后者接入 `/plans/production` 和 Profile 约束，镜头数、总帧数和显示时长取实际计划。固定参数展示为只读说明，不伪装可选控件。不得只将 6 改成 15 而仍保留 144 帧校验。
- 复验：5 秒基础计划=120 帧；15 秒生产计划=360 帧、5 镜头；界面、请求、冻结快照、ffprobe 一致；超出 Profile 范围生成前明确报错。

### BUG-02 / P1：提示词被保存，但未落实为执行计划；修改后仍可沿用旧分镜

- 状态：**真实成片/Manifest 不一致 + 代码确认**。
- 原因：`run()`（2231）PATCH intent 和原有 plan.shots，再审批、启动；不会重新解析描述。默认导演是本地相机规则，首页仍走 V1 模板。完整人物、场景、音频要求没有完成这条入口的执行编排。
- 修改：提示词变更后标记计划待更新并使旧确认失效；先解析并展示结构化场景、时长、动作、字幕/音频需求与能力覆盖，再允许确认。未支持的人物接触、投影或材料保真要求明确阻断正式广告或经用户选择降为预演；禁止静默降级为三镜头。
- 复验：同一宇航员 brief 必须生成 5 段对应时间范围；修改任一情节后旧分镜不可直接冒充新要求执行；人物/投影不支持时可见提示；完成状态分别列出技术输出、语义符合和产品保真结果。

### BUG-03 / P1：计划创建后更改分辨率，启动时不保存新输出参数

- 状态：**代码路径确认，未另起渲染验证**。
- 原因：`updateOutput()`（2257）只改 React output；`run()` PATCH 仅传 intent/shots/crop_anchor，未传 output。原计划仍保留创建时分辨率。
- 修改：统一编辑态与冻结计划；分辨率变更应更新合同并失效旧审批，或要求重建计划并禁用启动。显示“本次实际输出规格”。
- 复验：540×960 创建计划后改1080×1920，启动前请求/合同均为1080×1920，ffprobe确认；反向切换亦同。

### BUG-04 / P1：无外观信息的模型进入广告流程，材质缺口未在入口清楚暴露

- 状态：**真实 GLB 解析确认**；对 15 秒广告空间/几何问题沿用已有报告，不当作本轮新渲染证据。
- 原因：输入仅单一灰色材质且无 UV/纹理/顶点色。素材卡只显示“可执行三维环绕”，没有告诉用户外观未核验。
- 修改：展示外观来源、材质/纹理/顶点色可用性与参考一致性；灰模允许明确的几何预演，要求真实外观的广告需先完成材质/几何核验。不应简单地“无纹理一律拒绝”：无纹理也可能有正确 PBR 材质或顶点色，须按实际外观证据判断。
- 修复顺序：对照授权参考核查形状 → 修补可信材质与外观映射 → 同角度静帧确认 → 灯光/透视/接地阴影 → 视频与最终帧检查。不可把涂黑面罩冒充完整保真。
- 复验：宇航员参考与渲染并排对照，面罩/镜头/软管/喇叭/底座逐项记录；有缺口则禁止宣称正式保真成片通过。

### BUG-05 / P1：基础预演 Manifest 的 Strict 标识与实际验证状态冲突

- 状态：**真实 API/Manifest + 代码确认**。
- 实证：同一 Job 的 release_status 为 strict_mode=false、fidelity_complete=null、reason=V1/V2基础预演；director_plan.fidelity_mode=STRICT_REQUESTED，但 director_plan_3d.fidelity_mode=STRICT。
- 原因：`apps/api/productdirector_api/director_plan.py:189` 在目标文档中固定写 STRICT；product_version_id 缺失时也使用固定占位 UUID（178），本次与实际合同版本不同。
- 修改：区分 requested_mode、executed_mode、verification_status；传递真实版本绑定，缺失时标未知/报错。修订 schema/消费者，避免基础预演导出被解读为已验收 Strict。
- 复验：基础预演不能导出为已验证 Strict；真实严格链路必须具备实际合同/版本、证据与对应状态；Manifest、API、UI三方一致。

### BUG-06 / P1：批次参数修改或预览失败后，旧预览仍允许创建

- 状态：**浏览器复现 + 代码确认**。
- 复现：选 d302f094 + TikTok MX + 2 变体 → “预览展开”成功2项；改变体为3 → 旧预览仍显示2项，“创建并开始”仍启用。随后切计划预览报不相容，旧2项预览及创建按钮仍保留。
- 原因：form 更新未清空 preview；创建只检查 `busy || !preview`（App.jsx约819）；createBatch 使用当前 form 而不是已经核对的预览快照。
- 修改：任何矩阵/并发参数变动或预览失败立即失效 preview；预览绑定请求哈希和相关版本；创建前确认当前参数与有效预览一致，并由服务端复验。
- 复验：2→3后按钮禁用，重新预览显示3才可启动；取消全部Profile、换计划、改变并发、预览失败都不得沿用旧结果。

### BUG-07 / P1：批次切换计划后沿用旧产品版本，造成不相容错误

- 状态：**浏览器复现 + 代码确认**。
- 复现：d302f094 预览成功后切换“5 秒时长验证 · 79dbfd52”，再预览，提示“1 个组合不相容（已批准计划绑定固定产品版本）”。
- 原因：`packageSelectedPlanVersion` 及 useEffect（App.jsx约780）只在 product_version_ids 为空时加载；切 plan_id 不清旧版本。异步回调还使用旧 form 的整体展开，有覆盖用户期间勾选项的风险；本轮选计划后立即勾Profile首次未保留，第二次才生效。
- 修改：每次切换计划重新获取对应合同；加载中禁用预览/创建，使用函数式状态更新及过期响应保护；旧版本、旧预览同时失效。
- 复验：连续切换两个不同产品计划均绑定各自实际版本；慢响应/快速切换不回写旧选择；无需刷新页面即可正确预览。

### BUG-08 / P2：窄窗口侧栏无名称/提示，批量入口难以找到

- 状态：**真实 DOM/可访问性树 + CSS 确认**。
- 原因：styles.css:112–113 在≤1120px隐藏nav span，按钮无 aria-label/title；实际可访问性树出现20个无名按钮。
- 修改：所有导航保留明确 aria-label 与可见悬浮/键盘提示，提供可展开菜单。当前批量位置为左侧“批次生产”，在“平台配置”下方、“音频与音乐”上方。
- 复验：1024px、窄侧栏可识别并进入批次页，键盘/读屏可读名称；1440/1672px 保留完整名称。

### BUG-09 / P2：批次 Profile 选择只显示比例/语言，不能区分平台

- 状态：**浏览器复现 + 代码确认**。
- 实证：两项“9:16 · en-US”、两项“1:1 · es-MX”、两项“9:16 · es-MX”重复，选择前无法辨别平台；要到预览结果才看到 profile_key。
- 原因：BatchPage（App.jsx约802–808）标签只有 aspect_ratio 和 locale。
- 修改：显示平台名称、Profile名称/版本、比例、语言；测试草稿与正式配置分组并清楚标记。
- 复验：无需试选即可区分 TikTok/YouTube/Instagram/Facebook/Marketplace，支持键盘选择，选项名称不再重复混淆。
