日期：2026-09-11  
性质：施工顺序与验收组织方案；不替代主规格，也不表示新增功能已实现。  
当前状态：A01 已启动（环境与记录基线），并进入“可执行验收链路”准备；以下工作包为后续执行安排，当前仅变更基线与阶段记录，不代表 V1 代码与云端任务已完成。  
依据：[完整主规划](../ProductDirectorAI_V1-V6_Codex_Development_Plan.md)、[当前阶段](CURRENT_PHASE.md)、[实现差距](V1_IMPLEMENTATION_GAPS.md)及本次代码/测试检查。  

## 1. 目标与现有起点

目标是更快取得可用成果，并按 V1 → V2 → V3 → V4 → V5 → V6 完成验收。提速来自复用已有代码、一次做好通用基础、减少重复渲染、提前准备外部条件和集中验收。

已确认起点：

- V1 图片/GLB 上传、分镜编辑、冻结计划、Blender/FFmpeg 成片已有实现；云端 1080×1920、24fps、6 秒已有历史验收证据。
- 2026-09-11 本地分镜/输出规格复验 9/9 通过。新增任务测试因缺少 httpx 无法加载，尚未提交，不能计为可靠性通过。
- 用户于本次对话再次确认：云端已安装 MiniMax H3。云交接记录还记载独立 ComfyUI 量化环境及试验产物；本轮未重新登录云节点复验。
- H3 按“已安装、待项目接入”排期；不安排重复安装或重复下载。安装完成不等于项目已支持任务跟踪、失败恢复或产品保真。
- 当前执行器仍是 SQLite + FastAPI BackgroundTasks，主规格中的可靠 Worker、完整产品版本/计划合同及远程鉴权未完成。
- 原有工作台和渲染器继续使用。V1 总状态保持 PARTIAL。

## 2. 提速规则

1. 每个任务交付“可运行代码 + 对应测试 + 证据 + Git 提交”，完成后继续当前阶段下一任务，不在每个小步骤重复询问。
2. 先固定当前阶段的接口和数据合同，再并行准备其界面、测试夹具与文档；核心数据库、状态机由一条集成路径维护，避免互相覆盖。
3. 版本按顺序实施。未来阶段可以提前整理素材、账户条件、官方资料和验收清单，不提前开发未来业务，也不把准备工作计为验收。
4. 保留现有布局和可用渲染实现；新增字段按合同渐进接入。TypeScript、完整数据合同等原规格要求仍跟踪，不借“复用”删除必需项。
5. 普通回归先用短小夹具；正式阶段门按主规格跑完整真实链路。相同输入、代码及环境的有效证据可以引用，有关依赖变化后重跑受影响项。
6. 同一 GPU 初始只安排一个重负载任务；CPU 测试、文档、前端检查可同时进行。两个 Worker 的合同测试不等于两个 GPU 作业同时跑。
7. 用主规划原任务 ID 跟踪验收。历史日志中的“V1-06 输出分辨率”不能替代主规格 V1-06“队列与恢复”。
8. 用户继续到 V6 的授权持续有效；日常编码不重复索要授权。阶段工程证据完备记 READY_FOR_REVIEW，需用户判断的产品/人物/发布审批集中呈现，ACCEPTED 不代签。

## 5. H3 已安装后的 V2 接入顺序

进入 V2 后按下面顺序执行，不从安装开始：

1. 核对当前端点、服务健康、运行中队列、模型/节点/工作流版本和可用磁盘。保留其他正在执行的任务；现有试验成果只作参考。
2. 固定一份现有可运行 workflow 及其输入/输出字段，保存不含凭证的版本、模型引用和文件哈希。工作台用“生成背景/生成预览”等产品操作包装，不让用户填写节点 ID。
3. 接通“项目创建任务 → 提交 workflow → 保存 prompt/operation ID → 查询进度/历史 → 下载并校验视频 → 登记 Artifact”的完整链路。
4. 验证服务中断、下载失败、提交结果未知、取消能力。共享 ComfyUI 的全局中断不能当单任务取消；无法安全取消时明确返回能力限制，并追踪原任务。
5. 记录真实耗时、峰值显存、磁盘增量、分辨率、时长与失败次数，再确定单卡并发和后续容量安排。
6. AI Director 的结构化计划、校验、路由和模板回退仍独立实现；H3 成片成功不能替代计划合同通过。

ComfyUI 官方提供提交、prompt ID、历史查询和成果读取等接口，实际适配以已部署版本为准。[ComfyUI 官方服务路由](https://docs.comfy.org/development/comfyui-server/comms_routes)

H3 优先使用现有自托管环境。官方仓库将 H3-Base、托管 Context-IR 和 Regenerate-2K 分别说明，并采用 Community License；本计划只接入现场确实可用的能力，不假设它们全已部署。[MiniMax H3 官方仓库](https://github.com/MiniMax-AI/MiniMax-H3)

主规格 V2-03/06/07 仍要求本地 LLM、远程 LLM、MiniMax 官方视频接口与重建路径的真实验证。自托管 H3 不能同时替代所有这些验收。先做现有 H3 集成；其余项逐个核对可用配置与预算。若希望将官方付费 API 从必需项改为可选，需要单独确认范围并记录 ADR，本规划不自动删除原要求。

V2 验收样本沿用主规划：20 条描述，其中 10 条可执行样本至少 9 条在两次修复内得到可执行计划；所有真正入队计划必须通过服务端校验。无 AI 时 V1 模板链仍可用。

## 6. V3–V6 的最短实现路径

- V3：先做刚性带 Logo 产品、孔洞/细杆产品的多通道和 Strict 合成；透明/强反射按原规格实测后明确限制。前两类至少三镜头、两背景；产品变色、Logo 缺失、Mask/ID 错误、尺寸变化及缺帧都必须被发现。单图/多视图审核保留，不能以生成背面当真实证据。
- V4：先验证一个单人按按钮镜头的实际人物层和接触，再完善走近、击打、收回、庆祝和双人轮流场景。优先从已有许可素材或受控角色路线选择能通过质量门的实现。Proxy 距离/时序测试和真人成片两轮人工审核分别记录，完整动作范围不因先做一个样例而缩减。
- V5：切镜/时间戳/人工修订先行；把分析结果转换成已有 DirectorPlan，复用 V3/V4 生产链。10 条授权参考片测试硬切 F1 ≥ 0.90（±0.2 秒）；至少三条真实重演；保留时长时按主规格检查帧级误差。
- V6-A：先固定 Profile 与后期合同，再分别做字幕/配音/BGM和 Batch。按输入快照、相机、规格、渲染版本复用合格 Master；仅改文案/语言时重做必要后期，改镜头/安全构图时重新渲染。依原规格交付六种导出 Profile及 1×1×3×2 的六条真实成果。
- V6-B：复用 V1 可靠任务与事件，新增账本、Automation scope/限流和 Webhook 投递；不另建绕过 UI 审批的执行通道。100 项可靠性测试与六条真实生产样例分开统计，避免把合同测试当 100 条 GPU 成片。
- V6-C：框架完成后四个连接器分别实现、分别核对官方能力、分别真实验收。成功平台保持原记录，失败平台按可确认的状态处理。最后完成多平台部分失败和全版本回归。

V3/V4 是画面质量的主要不确定点。若首个完整样例失败，先依据问题帧修复该路线；同一失败原因连续出现两次就记录并比较另一条符合原合同的路线，不靠不断增加随机重试推进。

## 8. 排期与资源决定方式

现有证据不足以可靠承诺“几天到完整 V6”。先完成前三个工作包，分别记录编码、验收、返工和外部等待时间，再给出滚动工期区间；每期结束更新一次，不用代码行数或界面数量计算完成百分比。

- S：一个边界清晰、验证路径已知的工作包。
- M：一个跨前后端或单个真实集成工作包。
- L：数据库/恢复/模型质量/平台接入等需要拆分和验证的工作包。
- 预测依据：同类已验收工作包的实际用时、剩余依赖和故障情况；平台审核/用户素材等待单列，不承诺上限。
- 每轮只有一个主集成目标；有独立条件的本阶段检查可并行，避免多个未完成大改同时积压。
- H3 已安装，当前优先测现有配置；是否更换 GPU 或扩盘，依据真实显存不足、队列耗时、临时文件需求判断。云盘“约 19GB 可用”是历史记录，任何新任务前重新检查，不当实时值。
- V6 的并发目标在合同/CPU 测试与真实 GPU 运行中分别配置；不因启动两个 Worker 就要求购买第二张卡。

## 9. GitHub 与验收记录

每个工作包收尾执行：相关检查 → diff/敏感信息检查 → 明确文件提交 → 上传 → 查询远端提交并确认一致。未上传或查询失败必须保留准确状态。

- 主规格继续保留在原文件；本计划只组织顺序，不创建另一份产品定义。

- 每阶段区分 NOT_STARTED / IN_PROGRESS / FAIL / BLOCKED / PASS；准备好的接口、mock 测试或未运行测试不能记真实集成 PASS。

- 源码、工作流模板、脚本、脱敏报告进 GitHub；模型、运行数据、真实素材、密钥和成片不进源码仓库。

本次交付为规划与文档索引更新，不包含代码修复、模型安装、云部署、真实数据库迁移或平台发布；所有阶段状态维持原有事实。
